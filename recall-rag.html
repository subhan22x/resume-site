Recall RAG: Connecting Document Search and Data Analysis

Recall RAG is an AI assistant combining hybrid RAG search, ELT pipelines with dbt, and semantic-layer text-to-SQL to answer questions about vehicle recalls. An MCP server exposes its document retrieval and analytics tools to external AI agents.

Try the application · View the code

I built Recall RAG to explore how an AI assistant can answer questions that need both written explanations and numerical analysis. It uses public NHTSA vehicle-recall records and guidance, alongside sample parts and warehouse data, to demonstrate a workflow an operations team could use.

The distinction matters because “What does this recall notice say?” and “Which model year has the most recall campaigns?” require different approaches. One needs a relevant passage from a document; the other needs an accurate database query. Recall RAG brings both into a single conversation and shows the evidence behind the answer.

Designing the experience

My starting assumption was that users would know their question but would not necessarily know which document, table, or report could answer it.

I designed a three-panel interface around that workflow. Conversations sit on the left, the assistant occupies the middle, and supporting evidence appears on the right. Example questions introduce the different capabilities without presenting prewritten answers.

When the assistant searches documents, users can select a source to inspect the cited passage and open the PDF at the relevant page. When it queries structured data, the evidence panel shows the SQL and the business terms used to interpret the question. This lets a technical reviewer inspect the implementation without requiring every user to understand it before asking a question.

A separate workflow canvas shows how source data moves through cleaning and transformation into the tables the assistant queries. The MCP page explains the available tools and how an external agent can connect.

RAG: Finding the supporting passages

The document pipeline ingests recall narratives from the NHTSA API and an official PDF guide. It tracks document versions using content hashes, allowing unchanged material to skip repeated processing while retaining the source information needed for citations.

I split text into chunks of approximately 500 words with a 75-word overlap. PDF chunks stay within their original page, preserving page references and text coordinates. The overlap helps retain context when an explanation crosses a chunk boundary.

Retrieval combines PostgreSQL full-text search with vector search through pgvector. Keyword search helps with exact identifiers and terminology; embeddings help when a user describes something differently from the source. The system searches both independently, combines their rankings using reciprocal-rank fusion, and limits how many passages one document can contribute.

The language model receives the selected passages and their citation IDs to compose an answer. The interface also exposes retrieval details, including candidate counts and the embedding model, so the search process is visible.

Text-to-SQL: Answering questions about the data

For numerical questions, I built an ELT workflow that loads raw records into PostgreSQL and uses dbt to clean, join, and organize them into analytics tables. These models cover recall intelligence, estimated parts demand, stockout risk, and possible warehouse transfers.

A YAML semantic layer defines the available metrics, dimensions, filters, and calculations. For example, a recall count needs a clear definition because a single campaign can appear against multiple vehicle configurations. Counting rows would not necessarily count distinct recalls.

The model translates a question into a constrained, structured request using those definitions. Python code then compiles that request into SQL, validates its syntax and permitted table access, and executes it in a read-only transaction with a timeout and row limit.

This keeps calculations consistent across questions. It also makes the answer inspectable: users can see which metric was selected and the query that produced the result.

MCP: Making the same capabilities reusable

I added an MCP server so tools such as Claude, Codex, or Cursor can use the application’s retrieval and analytics capabilities.

It exposes three tools: search recall documents, query recall analytics, and check data freshness. Document searches return passages with citation information. Analytics queries return results alongside the compiled SQL and semantic definitions. Status checks report the state of the underlying data.

These tools reuse the application’s existing logic. They accept bounded requests and do not expose arbitrary SQL execution or unrestricted filesystem access. The MCP interface also records recent calls, making it possible to inspect which tool ran, how long it took, and whether it succeeded.

What I learned

This project helped me understand where retrieval ends and data modeling begins. A relevant passage can explain a recall, but reliable totals and comparisons depend on defining the data correctly beforehand.

I also learned that smaller chunks are not automatically better. They can improve precision while separating a statement from the context needed to interpret it. I built retrieval checks for expected sources and ranking, alongside analytics and adversarial checks for query behavior, rather than judging quality only by how convincing an answer sounded.

Finally, designing MCP tools made me think more carefully about interfaces. A useful tool needs a clear purpose, predictable results, and limits the application actually enforces. The same principle shaped the UX: users should be able to follow an answer back to the documents and calculations that produced it.
