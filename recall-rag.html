Recall RAG: Connecting Document Search and Data Analysis

Recall RAG combines hybrid document search, dbt-powered ELT, and semantic-layer text-to-SQL to answer vehicle-recall questions. An MCP server makes its retrieval and analytics tools available to external AI agents.

Try the application View the code

I built Recall RAG to explore how one assistant can handle both written explanations and numerical analysis. It combines public NHTSA recall records and guidance with sample parts and warehouse data.

“What does this recall notice say?” needs document retrieval; “Which model year has the most campaigns?” needs a precise database query. Recall RAG brings both into one conversation and shows the evidence behind each answer.

Designing the experience

I assumed users would know what they wanted to ask without knowing which document, table, or report contained the answer.

I designed a three-panel interface: conversations on the left, the assistant in the middle, and supporting evidence on the right. Example questions introduce the system’s capabilities without showing canned answers.

For document questions, users can inspect the cited passage and open the source PDF at the relevant page. For data questions, the evidence panel shows the SQL and semantic terms used. A workflow canvas visualizes the data pipeline, while the MCP page documents the tools available to external agents.

RAG: Finding the supporting passages

The pipeline ingests NHTSA recall narratives and an official PDF guide. Content hashes version documents, skip unchanged processing, and preserve the source metadata needed for citations.

I split text into roughly 500-word chunks with 75-word overlap. PDF chunks stay within their original page, preserving page references and coordinates.

Retrieval combines PostgreSQL full-text search with pgvector. Keywords handle exact identifiers; embeddings handle paraphrased questions. Reciprocal-rank fusion combines both rankings while limiting duplicate passages from one document.

The model receives selected passages and citation IDs. The interface exposes candidate counts and the embedding model so retrieval remains inspectable.

Text-to-SQL: Answering questions about the data

For numerical questions, an ELT workflow loads raw records into PostgreSQL, then uses dbt to build analytics tables for recall intelligence, parts demand, stockout risk, and warehouse transfers.

A YAML semantic layer defines approved metrics, dimensions, filters, and calculations. This prevents a metric such as recall count from being distorted by duplicate vehicle configurations.

The model maps each question to a constrained request. Python compiles it into SQL, validates syntax and table access, then runs it read-only with timeouts and row limits.

Users can inspect both the selected metric and the query behind the result.

MCP: Making the same capabilities reusable

I added an MCP server so Claude, Codex, Cursor, and other agents can use the same retrieval and analytics capabilities.

It exposes three tools: search recall documents, query recall analytics, and check data freshness. Results include citations, compiled SQL, semantic definitions, or source status as appropriate.

The tools reuse the application’s logic, accept bounded requests, and do not allow arbitrary SQL or unrestricted filesystem access. Recent calls record the tool, duration, result count, and status.

What I learned

This project clarified where retrieval ends and data modeling begins: passages explain recalls, but reliable totals depend on well-defined data.

I also learned that smaller chunks are not automatically better. Precision can come at the cost of context, so I added retrieval, ranking, analytics, and adversarial checks instead of judging answers by fluency alone.

Designing MCP tools reinforced the same lesson as the UX: capabilities need clear purposes, predictable outputs, and enforceable limits. Users should be able to trace an answer back to its sources and calculations.
