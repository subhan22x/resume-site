Building a Permission-Aware RAG Chatbot for Enterprise Knowledge

An internal knowledge assistant designed to retrieve the right sources for the right employee, while making its evidence and uncertainty clear.

Internal work for ENGIE, shared at a high level under NDA.

I worked with ENGIE Energy to build an internal RAG chatbot that uses the company knowledge base to serve employees the correct files and answers based on their permission level.

Many enterprise chatbots let users query a vector database, but do not account for:

  • updating files and project context, including team structure
  • permission hierarchies, where a senior manager may be able to question the chatbot about financials while a junior engineer cannot

I worked with project managers and technical teammates to address these and other company-specific structural constraints. The chatbot allows employees across teams and leadership levels to search internal documents through a chat interface while respecting their access level, preserving privacy, and citing the source material behind each response.

Designing for trust, not open access

The product assumption was that users would arrive with a specific work question, much as they would ask a project manager or senior teammate: “What is the process for this?” or “What are the deadlines for this subtask in this specific project?” The experience needed to feel conversational while updating as quickly as the internal files did. It could not fall back on stale cached data.

The user flow was designed around that:

  1. A user signs in and starts a new conversation or returns to an earlier one.
  2. They ask a question in plain language.
  3. The system resolves which document collections that user is permitted to access.
  4. It retrieves relevant passages only from those approved documents.
  5. The response makes its source clear through citations.
  6. Selecting a citation opens the source document and, when available, the cited page.

The core UX decision was to make uncertainty visible instead of hiding it. A response backed by company documents is labeled as such. If the system cannot find sufficient internal evidence and provides a general response, that is shown separately as general knowledge rather than presented as a company fact. This helps mitigate familiar LLM issues such as hallucination, overconfidence, and stretching weak evidence to accommodate a request.

Conversation history was also treated as a real product feature rather than an afterthought. Users can revisit, search, and continue prior chats, while the backend uses recent context to rewrite vague follow-up questions into better retrieval queries. The goal is to preserve the natural flow of a conversation without losing the precision required for search.

Administrators have a different workflow. They can manage users and access classes, upload or synchronize documents, decide which files or folders are visible to each class, and track whether a document set has been indexed. Assigning a folder can also grant access to its contents, reducing repetitive permission management while keeping the model’s search space deliberately scoped.

The architecture

StepComponent / process
1Approved files and SharePoint sources
2Extraction, OCR, chunking, and embeddings
3Postgres + pgvector, scoped by access class
4Python / FastAPI RAG service
5TypeScript / Express application API
6Next.js chat, citations, document preview, and admin UI

The frontend is built with Next.js, React, and TypeScript. It provides the chat interface, conversation history, citation chips, document preview panel, and administrative screens for managing users, document visibility, and uploads.

The application backend is an Express and TypeScript service backed by Microsoft SQL Server. It handles authentication, user roles, conversation persistence, file metadata, administrative controls, and the mapping between users, access classes, and allowed documents.

We kept semantic search separate from that transactional application layer. The RAG service is built in Python with FastAPI, LangChain, PostgreSQL, and pgvector. It processes PDF, Word, PowerPoint, and Excel files; PDFs can use OCR when needed. Documents are split into token-aware chunks, embedded, and stored with metadata such as file name, page or sheet location, version information, and access-class relationships.

The most important implementation detail is that access control happens before answer generation. A user’s memberships are resolved by the application backend, then sent to the RAG service as the allowed scope. The vector query only retrieves chunks connected to those permitted document groups. In other words, the language model never receives passages from documents outside the user’s allowed scope.

We also built the retrieval path around quality thresholds and explicit source modes. When retrieved documents are strong matches, the assistant answers from those documents and attaches citations. When no relevant internal information is found, the system can say so instead of inventing an unsupported conclusion. For weaker matches, general knowledge is visually separated from document-grounded answers. This was reinforced through prompt testing focused on professional tone, correct citation behavior, and admitting when the available information was not enough to support a conclusion.

The ingestion process was designed with operational reliability in mind. Files are versioned using hashes, allowing the system to avoid unnecessary reprocessing and retain a relationship between a document and its indexed version. During re-indexing, the system tracks active ingestion work and maintains snapshots so it can recover from failures instead of leaving an access class with a partially rebuilt knowledge base.

What I learned

This project changed how I think about enterprise AI. The difficult part is rarely calling an LLM. The difficult part is designing the surrounding system: permissions, document lifecycle, source traceability, conversation context, failure states, and a user interface that communicates confidence honestly.

As a software person, this was valuable because it pushed me beyond a simple “chat with PDFs” demo. I worked on a system where product design, frontend UX, backend authorization, retrieval quality, and privacy constraints all affected whether the AI was actually useful. That is the kind of AI product work I want to keep doing: practical systems that make information easier to use without making it less trustworthy.
